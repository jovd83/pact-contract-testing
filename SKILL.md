# Pact Contract Testing

Design and implement **consumer-driven contract tests** with [Pact](https://docs.pact.io/) in any supported language, and optionally drive the consumer expectations from an existing contract source (OpenAPI, XSD, WSDL, JSON Schema, Protobuf, AsyncAPI, GraphQL, Avro).

## Scope

This skill **does**:

- Scaffold and write **consumer** tests (generate a pact file) and **provider** verification.
- Derive consumer expectations and **matchers** from a contract source via `scripts/scaffold_from_schema.py`.
- Set up **message/event pacts** (Kafka, SQS, SNS, AMQP) using ports-and-adapters.
- Configure **bi-directional contract testing** (PactFlow: OpenAPI as the provider contract).
- Wire the **Pact Broker / PactFlow** lifecycle: publish, `can-i-deploy`, `record-deployment`, webhooks, pending/WIP pacts.

This skill **does NOT**:

- Replace integration, E2E, functional, or load testing.
- Validate provider business logic — only message **shape** (request/response structure).
- Generate a classic pact directly from a schema (Pact is code-first; see "Core mental model").

## Core mental model

1. **Pact is code-first and consumer-driven.** The contract (a *pact file* of *interactions*) is **generated by running the consumer's tests** against a Pact **mock provider**, then **replayed against the real provider** to verify it.
2. **Each interaction is independent** — one interaction per test. Dependencies are expressed as **provider states** (`"given user 123 exists"`), never by seeding data inside the test.
3. **Be liberal in what you accept**: use **matchers** (type, regex, `eachLike`) instead of literal values. Literal-only contracts are brittle.
4. **A schema does not generate a classic pact.** Schemas plug in two ways:
   - **Design source** — read the schema to scaffold the consumer DSL and derive matchers. The test still produces the pact.
   - **Bi-directional (PactFlow)** — the provider's OpenAPI spec *is* the provider contract; PactFlow verifies the consumer pact against it with no provider test code.
5. **Test the real client, not a throwaway request.** The consumer test must drive the **actual client class your app ships** against the mock server URL — never an inline `HttpClient`/`fetch`/`requests` call written just for the test. The point is to prove *your* code is compatible with the contract; a hand-rolled request proves nothing about the code that actually ships.

## Required inputs

Confirm these before writing tests (ask if missing):

- **Role**: is the target code a **consumer** (calls an API / publishes or consumes a message) or a **provider** (serves the API / produces the message)?
- **Interaction style**: synchronous **HTTP/REST**, **message/event**, **gRPC**, or **GraphQL**.
- **Language & build tool** (e.g. Java + Gradle, TS + npm, .NET + dotnet).
- **Contract source** (optional): path/type of OpenAPI, XSD, WSDL, JSON Schema, Protobuf, AsyncAPI, GraphQL SDL, or Avro file.
- **Broker**: Pact Broker / PactFlow URL + token (env `PACT_BROKER_BASE_URL`, `PACT_BROKER_TOKEN`), or "local only". **If no broker exists yet**, offer to provision one (`scripts/start_broker.*` → self-hosted Docker broker) or point at PactFlow — see "Pact Broker & CI/CD".
- **Versioning**: source of the app version (default: git commit SHA) and branch.

## Decision tree

```
Is the source code the CONSUMER or PROVIDER?
├─ CONSUMER
│   ├─ HTTP/REST .......... write a consumer test with the mock provider  → "Workflow", references/languages.md

└─ PROVIDER

                              contract; no provider test code

Have a contract source file (OpenAPI/XSD/WSDL/JSON Schema/Protobuf/AsyncAPI/GraphQL/Avro)?
```

## Workflow (HTTP consumer-driven lifecycle)

1. **Pick the role and style** using the decision tree. If a contract source exists, run the scaffolder (step 2); otherwise hand-write from the worked example.
2. **Scaffold from the contract (optional)**:
   ```bash
   python scripts/scaffold_from_schema.py --type openapi --input api.yaml \
       --operation "GET /orders/{id}" --lang java --role consumer --out src/test/...
   ```
   Review the emitted matchers — tighten regexes, widen literals.
3. **Write the consumer test**: define interaction (+ provider state) → register with mock provider → call the **real client code** → assert. A pact file is emitted on success. (Language snippets: `references/languages.md`.)
4. **Publish the pact** to the broker with version = git SHA + branch:
   ```bash
   ./scripts/publish_pacts.sh   # or scripts/publish_pacts.ps1 on Windows
   ```
5. **Verify on the provider**: load pacts via consumer version selectors, register **provider state handlers**, replay. Use **pending + WIP** pacts so new consumer expectations cannot break the provider build.
6. **Gate the deploy**:
   ```bash
   ./scripts/can_i_deploy.sh --pacticipant Foo --version $GIT_SHA --to-environment production
   pact-broker record-deployment --pacticipant Foo --version $GIT_SHA --environment production
   ```

Full broker/CI detail: `references/broker-and-cicd.md`. CI template: `assets/ci/github-actions.yml`.

## Worked example — Java / JVM (consumer + provider)

**Consumer** (JUnit 5 + `au.com.dius.pact.consumer.junit5`):

```java
@ExtendWith(PactConsumerTestExt.class)
@PactTestFor(providerName = "OrderService", pactVersion = PactSpecVersion.V4)
class OrderClientPactTest {

  @Pact(consumer = "OrderWebApp")
  V4Pact getOrder(PactDslWithProvider builder) {
    return builder
        .given("an order 42 exists")                       // provider state
        .uponReceiving("a request for order 42")
        .path("/orders/42").method("GET")
        .willRespondWith()
        .status(200)
        .headers(Map.of("Content-Type", "application/json"))
        .body(newJsonBody(o -> {
            o.integerType("id", 42);                        // type matcher, not literal
            o.stringMatcher("status", "OPEN|SHIPPED|CLOSED", "OPEN");
            o.eachLike("lines", l -> l.numberType("qty", 1));
        }).build())
        .toPact(V4Pact.class);
  }

  @Test
  @PactTestFor(pactMethod = "getOrder")
  void getsOrder(MockServer mock) {
    var order = new OrderClient(mock.getUrl()).fetch(42);   // REAL client code
    assertThat(order.id()).isEqualTo(42);
  }
}
```

**Provider** (JUnit 5 + `au.com.dius.pact.provider.junit5`):

```java
@Provider("OrderService")
@PactBroker(url = "${PACT_BROKER_BASE_URL}", authentication = @PactBrokerAuth(token = "${PACT_BROKER_TOKEN}"))
class OrderServiceVerificationTest {

  @BeforeEach
  void setTarget(PactVerificationContext ctx) { ctx.setTarget(new HttpTestTarget("localhost", port)); }

  @State("an order 42 exists")                              // state handler seeds data
  void order42Exists() { repository.save(new Order(42, "OPEN")); }

  @TestTemplate
  @ExtendWith(PactVerificationInvocationContextProvider.class)
  void verify(PactVerificationContext ctx) { ctx.verifyInteraction(); }
}
```

Gradle dependency: `testImplementation 'au.com.dius.pact.consumer:junit5:4.6.+'` and `...pact.provider:junit5:4.6.+`.

## Matchers, provider states & message pacts

Use matchers, not literals. Spec-version matcher tables, provider-state patterns, and the **message/event pact** (ports-and-adapters) pattern are in `references/matchers-and-states.md`.

## Test derivation modes

A contract test always runs the same way, but the interactions can be **derived** from different sources. Pick by what you have (full guide: `references/derivation-modes.md`):

- **Code-driven** (Pact default) — wrap the consumer's real client call; the call shapes the interaction.
- **Schema-driven** — derive request shape + matchers from a contract source (see below).
- **Requirements-driven** — map use cases / user stories / Gherkin: `Given`→provider state, `When`→request, `Then`→response matchers.
- **Cookbook-driven** — apply reusable recipes (auth header, pagination, problem+json error envelope, idempotency key, timestamps).

Modes combine: code-driven structure + schema-driven matchers + cookbook recipes is common.

## Schema-driven & multiple contract types

A contract test can be derived from any of these sources; each maps to a specific Pact mechanism. Full mapping, scaffolding rules, and limits in `references/schema-driven.md`:

| Contract source | Domain | Pact mechanism |
|---|---|---|
| OpenAPI / Swagger | REST/JSON over HTTP | Consumer test (HTTP) **or** bi-directional (provider) |
| JSON Schema | Any JSON payload / event | Matchers for HTTP or message pacts |
| XSD | XML / SOAP / public-sector | HTTP + **XML matchers** (`bodyXml`), design source |
| WSDL | SOAP service description | XML matchers + extract operations/endpoints |
| Protobuf / gRPC | Binary RPC | V4 **pact-protobuf-plugin** |
| Avro | Kafka schemas | V4 **pact-avro-plugin** (message pact) |
| AsyncAPI | Event-driven (Kafka/AMQP) | **Message pact**, design source |
| GraphQL SDL | GraphQL | HTTP POST consumer test (query + variables matchers) |
| Pact files | Existing CDC | Verify directly / republish to broker |

Run the scaffolder first when a source exists:
```bash
python scripts/scaffold_from_schema.py --type <openapi|jsonschema|xsd|wsdl|protobuf|avro|asyncapi|graphql|pact> \
    --input <file> --lang <java|js|dotnet|go|python> --role <consumer|provider> --out <path>
```

## Pact Broker & CI/CD

The broker is a **separate application** (not a test dependency); the skill publishes/verifies *against* it. It shares pacts, records verification results, and powers `can-i-deploy` (reads the **matrix** to gate deploys).

**You must supply a broker.** If the user doesn't have one yet, pick:

| Situation | Action |
|---|---|
| Already have a broker (PactFlow / org-hosted) | Just set `PACT_BROKER_BASE_URL` (+ token or user/pass). **Don't provision another.** |
| No broker, want managed / bi-directional | PactFlow (free Developer plan): set `PACT_BROKER_BASE_URL` + `PACT_BROKER_TOKEN`. |
| No broker, local / on-prem / no-cloud | Provision a self-hosted Docker broker: `./scripts/start_broker.sh` (or `.ps1`). It boots `assets/broker/docker-compose.yml` (postgres + `pactfoundation/pact-broker`, persistent volume), waits for health, and prints the env vars to export. |

Self-hosted broker defaults are localhost-only basic auth (`pact`/`pact`) — **change them before exposing the broker beyond localhost** (`assets/broker/README.md`). Versioning, consumer version selectors, webhooks, pending/WIP, and environments are in `references/broker-and-cicd.md`. Helper scripts: `scripts/start_broker.*`, `scripts/publish_pacts.*`, `scripts/can_i_deploy.*`.

## PactFlow (managed broker + extras)

PactFlow is the **commercial broker** (SaaS or self-hosted) — a superset of the OSS Pact Broker. Everything above (publish, verify, `can-i-deploy`, `can-i-merge`, webhooks) works against it unchanged; these capabilities are **PactFlow-only** and are where the consumer/provider loop alone isn't enough:

- **Bi-directional contract testing** — when you only have the provider's **OpenAPI spec** and cannot run provider verification, PactFlow treats the spec as the provider contract and cross-verifies each consumer pact against it (`consumer pact ⊆ spec`). No provider test code, no replay. The OSS broker does **not** support this. Config + publish commands: `assets/pactflow-bidirectional/`; routing in `references/schema-driven.md` §Bi-directional. This is the answer when a provider team refuses to add Pact verification.
- **PactFlow AI** — generates consumer test scaffolding from an OpenAPI spec or sample requests. Treat its output exactly like `scripts/scaffold_from_schema.py`: a reviewed **starting point** (tighten matchers, set provider states), never a finished test.
- **Encrypted secrets** for webhooks — store broker/provider tokens in PactFlow instead of committing them.
- **Governance** (self-hosted PactFlow): RBAC, SSO/SAML, audit logging — the usual fit for regulated / no-public-cloud orgs that still want a managed broker rather than raw OSS.

Choosing: already on PactFlow → use it. Need bi-directional or governance → PactFlow (managed, or self-hosted for no-cloud). Plain consumer-driven CDC with no such needs → the OSS broker is complete (see the broker decision table above). Full feature detail: `references/advanced-features.md` §7.

## Advanced features

Beyond the basic loop, Pact supports (full guide: `references/advanced-features.md`):

- **Generators & `fromProviderState`** — produce values at replay time; inject server-generated ids the provider owns into the request.
- **Request filters** — inject auth (bearer/HMAC/custom headers) when verifying a secured provider, without baking credentials into the contract.
- **V4 synchronous messages** — request/response messaging (gRPC, RPC-over-queue) distinct from async events.
- **Plugin framework** — extend Pact to new transports/protocols (Protobuf/gRPC, Avro, CSV) via `pact-plugin-cli`; requires V4.
- **`can-i-merge`** — trunk-based variant of the deploy gate; plus `--build-url` verification metadata.
- **Webhooks, PactFlow bi-directional + AI, telemetry (`PACT_DO_NOT_TRACK`)**.

Reach for these only when a concrete need appears — the basic consumer/provider loop covers most cases.

## Anti-patterns to refuse

- ❌ Claiming you can generate a **classic pact directly from OpenAPI/XSD** — use the scaffolder (design source) or **bi-directional**.
- ❌ Treating Pact as **schema validation, functional, or E2E** testing.
- ❌ **Over-specifying** with literal values instead of matchers.
- ❌ **Multiple interactions per test**, order-dependent tests, or data seeded inside the test instead of provider states.
- ❌ Sharing pact files by **copy-paste** instead of a broker.
- ❌ Verifying only the **latest** pact (ignoring WIP/pending).
- ❌ **Hardcoded broker credentials**; reversing the **consumer/provider** direction.
- ❌ Legacy **tags-only** deploy gating instead of environments + `record-deployment`.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Consumer test fails: "missing request" | Client never hit the mock, or wrong path/method | Point the client at `mockServer.getUrl()`; match path/method exactly. |
| Provider verify fails: body mismatch | Literal expected value differs | Replace literals with type/regex matchers in the consumer test. |
| Provider verify fails: "state not found" | Provider state handler missing | Add a handler for every `given(...)` string used by consumers. |
| `can-i-deploy` exits 1 | No verification result for that version, or a failure recorded | Ensure the provider verified the consumer version; check the broker matrix. |
| Pact not appearing in broker | Publish step skipped or wrong version | Run `publish_pacts.*`; confirm `PACT_BROKER_BASE_URL`/token. |
| Provider build broken by a new consumer | Pact verified as required, not pending | Enable **pending** + **WIP** pacts in the verifier. |
| gRPC/Avro interaction won't record | Plugin not installed | Install `pact-protobuf-plugin` / `pact-avro-plugin` and use V4. |
| XML/SOAP body mismatch | JSON matchers used for XML | Use XML body matchers (`bodyXml` / `PactXmlBuilder`). |
| `429`/auth from PactFlow | Bad/missing token | Set `PACT_BROKER_TOKEN`; never hardcode it. |
